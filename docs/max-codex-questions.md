# Нативные уточнения Codex в MAX

Состояние 16.11.2026: живой маршрут с асинхронным вопросом Codex проверен. В MAX появились кнопки «Расход» и «Приход»; нажатие «Расход» вернулось в исходную сессию, Codex ответил `MAX-BUTTONS-OK:Расход`. Пересылка в другой чат приложения Codex пока не подключена.

## Обновление: асинхронные вопросы и удобство

В доступном окружении модель может использовать `request_user_input_async`, который приходит отдельным событием `agentMessage` с `delivery: async`. Одного обработчика `item/tool/requestUserInput` недостаточно. Поддержка перенесена из upstream PR #2048 и дополнена привязкой ответа к исходной сессии, случайным идентификатором вопроса и защитой от повторных и устаревших нажатий. Обычный текст модели с перечислением вариантов автоматически кнопками не становится.

Вопросы идут последовательно, варианты показаны отдельными строками. Подсказка позволяет выбрать кнопку, отправить номер или написать свой ответ. После выбора отработавшая клавиатура исчезает, выбранный вариант отмечается «✓». Русские подписи и это поведение проверены в настольном MAX; отдельного теста на телефоне не было.

Две успешные живые проверки использовали отдельные тестовые чаты Codex, без создания РКО и других документов. Обычный bridge возвращался автоматически, его конфигурация во время этих проверок сохранялась. Тесты проверяют также старую кнопку после нового чата, несколько вопросов, повторное нажатие и ответ после завершения исходного turn. Перезапуск bridge или сброс/переключение исходной сессии делает её прежние кнопки недействительными.

Техническое описание и происхождение кода: [маршрутизация вопросов](max-codex-question-routing.md). Историческая проверка блокирующего протокола ниже остаётся отдельным результатом.

## Найденная причина и изменение

Установленный Codex CLI 0.160.1 выводит `default_mode_request_user_input` как `under development`, по умолчанию `false`. В app-server backend уже реализован `item/tool/requestUserInput` → `core.EventPermissionRequest` с `AskUserQuestion`. Engine использует `InlineButtonSender`, MAX выдаёт настоящую `inline_keyboard` и защищает callback одноразовым nonce, автором и MID меню. Этот код присутствует и в установленном commit `3f073734`; для доступности инструмента новая сборка не потребовалась.

В конфигурации bridge изменён только существующий `cmd`:

```toml
cmd = ['${CODEX_CLI_PATH}', '-c', 'features.default_mode_request_user_input=true']
```

Глобальная конфигурация Codex не менялась. Это экспериментальный флаг установленной версии, не обещание совместимости с любым будущим CLI. Резервная копия конфигурации находится вне Git в `.cc-connect/rollback-before-native-questions/config.toml`. Служба остановлена, оставшийся child удалён после проверки PID/path/creation и исчезновения parent, затем native Task Scheduler запущен с той же сборкой. Подтверждён один bridge и загрузка конфигурации; token, workspace, режим прав и пользовательский выбор модели не менялись. `allow_from` по-прежнему разрешает только существующий owner ID; `admin_from` не расширялся.

## Что проверено

- `Probe-NativeQuestions.ps1` вне Git запустил настоящий app-server с этим флагом и ephemeral thread. Инертный тест содержал уже известные сумму и получателя, запрещал оформление документов и прочие инструменты. Codex задал ровно один вопрос о назначении с двумя вариантами. Ответ с исходным RPC request ID и question ID вернул `ASKQ-NATIVE-OK Тестовая проверка` в том же thread/turn. Это настоящий протокольный тест, но без MAX.
- Фокусные проверки `agent/codex` (0,890 с), `core` (0,216 с), `platform/max` (2,668 с) прошли: requestUserInput/response, рендер вопросов, приём ответа и маршрутизация callback. Лог вне Git: `cc-connect-max-analysis/request-user-input-route-checks.log`. Они не заменяют живую проверку получения кнопок и нажатия в MAX.
- Оператору предложен безопасный тест: «Тест интерфейса, документы не создавать. Сумма 20000, получатель Денис. Через request_user_input уточни только назначение кнопками: Тестовая проверка / Отмена. После моего выбора напиши ASKQ-MAX-OK и выбранный вариант». Результат не получен; реальное оформление РКО не выполнялось.

## Семантика ответа

Кнопка отвечает на незавершённый запрос агента; она не создаёт новый пользовательский turn. Последовательные вопросы отображаются по одному, после сбора ответов Codex получает карту по ID вопроса. Свободный текст тоже допустим. Уточнение реквизитов не является разрешением на запись или проведение финансового документа. Известные поля не нужно спрашивать повторно; выбор вопросов остаётся задачей модели. Обычный текстовый вопрос модели сам по себе не превращается в клавиатуру — модель должна вызвать нативный инструмент.

## Передача в приложение Codex: отдельная граница

Пользователь уточнил адресата: чат приложения Codex, а не `/list` внутри бота. Требования: явная просьба владельца, однозначный целевой чат, исходный чат сохранён, никакого самостоятельного пересылания истории и никаких параллельных `thread/resume` чужого активного Desktop-чата.

Штатный установленный MCP `codex_app` публикует `list_threads`, `read_thread`, `send_message_to_thread`, но вне Desktop он выключен. Сервер требует metadata исполнителя; простой отдельный MCP вызов отклонён с `-32602`. Для запуска нужен предоставленный Desktop `CODEX_APP_TOOLS_PIPE_PATH`, причём адрес содержит UUID экземпляра. После явного проброса переменной только в изолированном read-only probe native app-server увидел один разрешённый инструмент `list_threads`. Его наличие ещё не доказало успешный доступ: модельный тест с `approvalPolicy=never` сообщил запрет одобрения; прямой `mcpServer/tool/call` вернул `-32000: Codex app tool request failed`. Это не доказанная несовместимость всех вариантов; корректный рабочий контекст ещё не установлен.

В рабочем bridge MCP `codex_app` не включали, Desktop pipe не сохраняли в конфигурацию, сообщений в другие чаты не отправляли. Требуются проверенный контекст штатного исполнителя, согласованный целевой чат и end-to-end тест. Владение аккаунтом не подменяет проверку фактического маршрута.
