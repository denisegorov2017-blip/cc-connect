# Голосовые MAX → Codex: рабочий контракт и доказательства

Состояние 16 ноября 2026: **production readiness не доказана**. Рабочая текстовая сборка `3f073734` не изменена. Цель создана по поручению пользователя; тестовый материал — уже отправленная запись, новые записи вместо неё не требуются.

## Проверено до реализации

1. Официальная схема MAX описывает `AudioAttachment.transcription` рядом с `payload`: строка nullable. У `payload` есть `url`/`token`. Непустая расшифровка может идти в Codex без скачивания аудио и STT; её наличие не гарантируется.
2. `GET /messages?chat_id=567855475&count=100` не содержит исходного audio. `GET /messages/{originalMid}` возвращает HTTP 200 с `code=empty.response.body`; `GET /messages?message_ids={originalMid}` — пустой массив. Повторное точечное чтение после клиентской расшифровки не дало тела сообщения. Проверка обоих MAX API hosts дала одинаковую ошибку; рабочий host остаётся документированным `platform-api2.max.ru`.
3. GET пересланного сообщения возвращает пустой `body.text`, без attachments; `link.message` содержит только исходные `mid`/`seq`. Из этих данных невозможно восстановить аудиобайты или расшифровку. Причина отсутствия медиа в Bot API пока не установлена; успешное чтение текстов и пересылки не доказывает исправность доставки audio.
4. Текущий adapter не читает `AudioAttachment.transcription`, использует недокументированный `/audios/{token}` при отсутствии URL и рано расходует in-memory dedup. Webhook подтверждается до durable обработки. Эти дефекты требуют отдельных отрицательных/повторных/recovery проверок; исправление только STT не устраняет проблему исходного материала.
5. `GET /subscriptions` вернул пустой массив. Работает один polling bridge. В текущем Hermes config нет публичного webhook URL; local 8646 listener и cloudflared/ngrok/caddy processes не обнаружены. Документация MAX рекомендует webhook и прямо не относит long polling к production. Нельзя объявить текущий polling production-ready или молча добавить новый внешний tunnel.
6. В установленном Hermes уже есть transcript-first реализация и регрессии: `plugins/max-platform/docs/transcript-first_RU.md`. Её документация отдельно фиксирует прежнее такое же расхождение GET для audio. Это полезный образец обработки, но не доказательство текущей доставки cc-connect. Hermes runtime и настройки не менялись.
7. Установленный Codex CLI **0.160.1** сгенерировал собственную JSON schema: `TurnStartParams` принимает `audio` с `url` и `localAudio` с `path`. Experimental realtime также есть, но не требуется для конечной голосовой записи. Схемы вне Git: `%LOCALAPPDATA%/cc-connect-max-analysis/codex-01601-schema`. Поддержка формата в протоколе ещё не доказывает доступность аудио выбранной модели или успешный запрос.
8. Реальный read-only `model/list` установленного app-server в 03:50 завершён без ошибок и cursor. Все 10 доступных моделей, включая terra, объявляют `inputModalities=[text,image]`, без audio. Это существенное ограничение: нельзя включить `localAudio` только потому, что variant присутствует в JSON schema. Проверочного model turn с исходной записью пока нет. Inventory завершил собственный процесс; основной bridge не менялся. Evidence вне Git: `candidate/native-audio-capabilities.json`.

## Следующие проверяемые этапы

1. Разрешить production архитектуру получения audio: документированный webhook, auth, durable admission/ограничения и исходная запись. Установить доступный способ получения исходного файла без ручной подмены текста и без неофициального userbot как незаявленного fallback. Если нужны внешний endpoint или права — сначала показать конкретный вариант и запросить недостающее решение.
2. Регрессия → исправление transcript-first в единственном MAX adapter: авторизация/дедуп до обработки, непустой transcript без download/STT, подпись и другие вложения сохранены, пустой/null/invalid transcript сохраняет аудиопуть. Не превращать произнесённую строку в обход admin/approval политики.
3. Проверить нативный Codex audio/localAudio на исходном файле и выбранной модели. Только подтверждённый путь включать в канонический optional-capability контракт core/agent; exec не должен притворяться поддерживающим аудио. Не подключать платный STT и не извлекать auth для неофициальных API.
4. Ошибки download/размера/формата/timeout и повторная доставка: понятный русский результат, секреты/подписанные URL не логируются, повтор не запускает второй turn, recovery не теряет уже принятую запись. Хранение и cleanup ограничены и принадлежат одному владельцу.
5. Измерить на этой же записи получение → transcript/audio processing → Codex first/completion → MAX delivery. Сначала serial baseline, затем изменения только измеренного bottleneck; сравнивать одинаковый материал. Готовый transcript предпочтителен как устранение ненужной работы, но заявление ускорения требует живых замеров.
6. Регрессии, CUJ через ReceiveMessage, vet, owning gates; точный commit/archive build; safe install и live end-to-end именно на исходной записи; restart/rollback и итоговая матрица. Старое исключение для локального коммита не превращает непрошедший release gate в успешный.

## Следующий checkpoint: ошибки вложений и размещение

- Регрессия показала caption-only ошибку при `audio` без URL: предыдущий код терял аудио и передавал подпись как успешный запрос. Теперь ошибка входа передаётся каноническому Engine как `Message.InputError`; пользователь получает локализованное сообщение, агент не запускается. Повреждённые/недоступные вложения не превращаются в частичный запрос; signed URL не входит в reason лога.
- `AudioAttachment.Caption` отделяет авторскую подпись от recognition text. MAX передаёт её отдельно; при настроенном STT Engine сохраняет подпись вместе с результатом. При выключенном STT подпись не подменяет распознавание. Недокументированный audio-token endpoint исключён. Нормализуются MIME с параметрами; пустой audio, HTML вместо audio и несколько нерасшифрованных audio отклоняются.
- Проверки: core 26,885 с, Codex 14,207 с; финальный MAX 8,443 с; vet core/Codex/MAX прошёл; отдельный CUJ 3,503 с. CUJ-A4 теперь покрывает три действия пользователя: ошибка получения → raw voice без STT → готовый transcript с ответом. Дополнительный тест проверяет сохранение caption после STT. Это офлайн-проверки; исходная запись ещё не прошла live pipeline.
- После ответа пользователя «существующего адреса нет, подбери размещение» сравнены актуальные официальные документы. KeenDNS: бесплатный постоянный адрес и проксирование локальных web-приложений даже при private WAN IP; пригодность конкретной конфигурации для MAX HTTPS:443/POST/secret-header требует проверки. На локальном gateway `192.168.1.1` получена страница `KeeneticOS Web Panel`, запрос версии требует авторизации (401). Настройки не менялись, пароль не подбирался.
- CloudPub: бесплатный постоянный поддомен, автоматический SSL, Windows client, заявленный тарифный трафик 250 ГБ/месяц. ngrok: бесплатный статический dev domain, 20 000 HTTP запросов/месяц и 1 ГБ; нужен аккаунт. Cloudflare Quick Tunnel временный и не предназначен для production, полноценный Tunnel требует домен. VPS — платный отдельный сервер; сохранённый Windows-Codex всё равно зависит от доступности ПК, если не переносить выполнение. Никакие аккаунты, DNS, подписки и внешние публикации не создавались.

Рекомендуемый следующий read-only этап — проверить настройки KeenDNS через штатный интерфейс роутера; затем подготовить отдельный webhook hostname на Windows и проверить реальный POST с заголовком секрета перед переключением бота. Выбор маршрута не доказывает исправление исходной аудиодоставки.

## Keenetic и локальная проверка webhook ingress, 16.11.2026

- В авторизованном web UI подтверждены Keenetic Viva KN-1910, KeeneticOS 5.1.6, существующий KeenDNS с SSL, включённый прямой доступ и HTTPS-порт 443. WireGuard VPN-сервер и SSTP показывают «Работает». Новых web-приложений не добавляли; публикация, firewall, VPN, обновление роутера и подписка MAX не менялись. Точный проект маршрута хранится вне Git в `cc-connect-max-analysis/keenetic-probe/route-plan.json`. Ответ пользователя с вопросом о VPN не является разрешением на публикацию.
- MAX требует достижимый HTTPS:443 endpoint; закрытый VPN сам по себе не предоставляет такой endpoint внешнему отправителю. Вариант VPS с очередью и закрытой связью через WireGuard предложен как архитектура, не выбран и не развёрнут. Публичный приёмник с сохранением перед ACK, ограниченной асинхронной обработкой и дедупликацией отделяет доступность доставки от доступности Windows. Существующие правила и подключения не переиспользуются без проверки области доступа.
- Четыре регрессии воспроизвели дефекты: JSON с хвостом за лимитом 4 MiB получал 200 после усечения; malformed JSON записывался в лог вместе с payload; занятый порт не мешал успешному POST subscription; ошибка subscription сохраняла HTTP server. RED: `voice-webhook-ingress-red.log`, четыре провала.
- Исправление локальное: TCP listener открывается до subscription; при отказе регистрации listener закрывается и поле server очищается. HTTP body ограничен через `MaxBytesReader` с 413 для превышения; ошибки чтения и JSON содержат только фиксированный reason, без тела запроса. Ограничены read/write/idle timeout и размер заголовков. Регрессия отказа подписки проверяет готовность listener в момент регистрации и освобождение того же порта после ошибки.
- Проверки: полный MAX package 8,694 с успешно (`voice-webhook-max-final.log`); `go vet ./platform/max` и `git diff --check` успешно. Эти изменения ещё не установлены. Старое исключение для локального коммита действует; общий all-platform Windows gate не объявляется успешным.
- Восстановление принятого события всё ещё НЕ РЕАЛИЗОВАНО: текущий handler отвечает 200 перед асинхронной обработкой, durable admission отсутствует, дедуп процессный. Исправления ingress не доказывают recovery, live TLS/POST/header forwarding или прохождение исходной записи. Production acceptance остаётся незавершённой.

## Разрешённый KeenDNS test: граница прав Windows

- Пользователь явно разрешил временный маршрут KeenDNS на Windows TCP 8647 и узкое правило только от роутера, с удалением новых настроек после проверки. Это разрешение не включает переключение MAX subscription.

Подготовленный вне Git `keenetic-probe/Temporary-Firewall.ps1` проверяет hash exe, создаёт только точное правило program/local IP/port/remote IP, читает filters обратно и удаляет своё правило при stop marker либо через 15 минут. Syntax и отрицательная проверка без admin token прошли без изменения firewall.
- Штатный запуск Windows PowerShell с `RunAs` завершился сообщением «Операция была отменена пользователем». Process handle elevated helper не создан, его state отсутствует. - Независимая read-only проверка уже зарегистрированного домена прошла: стандартный `SslStream` без callback обхода доверия установил TLS 1.3 на 443, сертификат Let's Encrypt YR1, действителен до 01.01.2027.
